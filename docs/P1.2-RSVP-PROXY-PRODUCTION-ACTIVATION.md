## Resumo executivo

A activação consiste em ligar o proxy no Edition (`HAXR_API_BACKEND=proxy`) depois de o Core produção estar live com auth proxy e Trusted Sources OIDC. O rollback é instantâneo: voltar a `local` + redeploy Edition, sem tocar na base de dados.

**Recomendação:** plano executável — activação bloqueada até pré-condições e Pre-T0 Baseline Snapshot completos.

#### C2 — Core Production unauthenticated verification

**Regra operacional:**

O teste **sem** header `Authorization` deve devolver **HTTP 401** com **`Content-Type: application/json`** **pela rota Core** (`/api/v1/edition/rsvp`), quando executado pelo **mecanismo operador autorizado** (contract CLI com bypass de automação, ou outro caminho interno aprovado — **nunca** bypass no runtime Edition→Core).

Uma página **HTML**, **login SSO** ou **redirect da Vercel** significa que a **Deployment Protection interceptou o pedido antes do Core**. Isso **não** é falha de auth Core nem critério NO-GO por si só — repetir a verificação pelo mecanismo autorizado que atinge a rota.

**Pedido de referência:**

```http
POST https://www.haxrsignature.com/api/v1/edition/rsvp
Content-Type: application/json

{"slug":"despedida-de-solteira","name":"","attending":true,"guests":1}
```

**Critérios GO (todos obrigatórios — resposta da rota Core, não da Protection):**

| Campo | Expected |
|-------|----------|
| HTTP status | **401** |
| Content-Type | **application/json** |
| Body | envelope JSON genérico, ex.: `{ "success": false, "error": "Não autorizado." }` |
| Prova de rota | Log Core `[api/v1/edition/rsvp] proxy auth failed` ou equivalente com `requestId` |

**Interpretação — o que NÃO conta como C2:**

| Resposta observada | Significado | Acção |
|--------------------|-------------|-------|
| HTML / login Vercel / redirect SSO | Protection **antes** do Core | Não classificar como falha auth Core; usar mecanismo operador autorizado |
| `200` HTML | Idem | Idem |
| `401` sem `application/json` | Resposta não veio da rota Core API | Repetir via mecanismo autorizado |

**Deployment Protection:** manter sempre activa. C2 valida auth proxy **no Core**, não a ausência de Protection.

## 5. Monitorização — 72 horas

### 5.1 Edition — `scope=edition/rsvp/proxy`

| Métrica | Threshold alerta |
|---------|------------------|
| `outcome=forwarded` | Dominante (>95%) |
| `outcome=network_error` | >5% em 15 min |
| `outcome=timeout` | >1% em 15 min |
| `outcome=invalid_core_response` | Ver **5.3** e triagem |
| `proxyLatencyMs` p95 | Warn se >5000ms |

### 5.2 Core — `[api/v1/edition/rsvp]`

| Métrica | Threshold |
|---------|-----------|
| `proxyOrigin: edition` | Presente em pedidos Edition |
| HTTP 5xx | Ver **5.4** |
| `requestId` | Correlacionável com Edition |

### 5.3 `invalid_core_response` — incidente e rollback

**Regra stricta:** este outcome pode indicar interceptação HTML/SSO em vez de JSON Core.

- Qualquer `invalid_core_response` **após T0** abre **incidente imediato**.
- Investigar: `requestId`, upstream host, content type, redirect status, logs Core.
- **Rollback** se `invalid_core_response` **se repete ou persiste >5 minutos**.
- **Um evento isolado** durante transição de deployment **não** força rollback automático, mas **não pode ser ignorado** — registar, triagem completa, reavaliar em 15 min.

### 5.4 Rollback — critérios 5xx (tráfego baixo)

Rollback se **qualquer** condição for verdadeira:

1. **≥3 falhas 5xx** RSVP (Edition proxy ou Core) **dentro de 15 minutos**; **OU**
2. Taxa 5xx **>1%** sobre **≥20 pedidos POST RSVP** numa janela de **15 minutos**.

**Nota:** não interpretar **uma falha 5xx isolada** como percentagem significativa em tráfego RSVP muito baixo.

### 5.5 Correlacionação requestId

Edition `requestId` → Core log `[api/v1/edition/rsvp] Processed { requestId, status, proxyOrigin }`.

### 5.6 Triage — incidente `invalid_core_response`

1. Capturar **Edition `requestId`**.
2. Verificar campos Edition:
   - `trustedOidcPresent`
   - `upstreamStatus`
   - `upstreamContentType`
   - `upstreamRedirected`
   - `upstreamFinalHost`
3. Procurar o **mesmo `requestId`** nos logs Core.
4. Classificar falha:
   - antes da rota Core (Protection / SSO / HTML);
   - auth proxy Core;
   - validação/persistência Core;
   - reencaminhamento de resposta Edition.
5. Aplicar rollback segundo **5.3** e **5.4** se thresholds atingidos.

## 7. Go / No-Go

### GO — activar proxy (T0)

Todos obrigatórios:

- [ ] C1–C16 pré-condições verdes
- [ ] **C2 returns 401 JSON, not HTML/SSO** (ou validação equivalente via caminho operador aprovado)
- [ ] **Pre-T0 Baseline Snapshot captured and stored**
- [ ] **Deployment IDs for Core and Edition recorded** (B1, B2)
- [ ] **Resend and Supabase baseline checked** (B4–B6)
- [ ] **Incident owner and rollback operator identified**
- [ ] C5/C6 Trusted Sources Production confirmados
- [ ] C8 secret alinhado · C10 `HAXR_PROXY_FALLBACK=false`
- [ ] Operador disponível 2h pós-T0
- [ ] Rollback drill Preview documentado

### NO-GO — abortar activação

- Core não devolve 401 JSON (após exclusão de falso positivo HTML/SSO)
- Baseline Snapshot incompleto
- Secret mismatch · `HAXR_PROXY_FALLBACK=true`
- Contract tests não verdes (24h)
- Incident owner / rollback operator não designados

### NO-GO — rollback pós-activação (72h)

- `invalid_core_response` repetido ou >5 min (secção 5.3)
- 5xx secção 5.4
- Duplicados guest/email atribuíveis ao switch
- Smoke S1/S2 falha após T0
